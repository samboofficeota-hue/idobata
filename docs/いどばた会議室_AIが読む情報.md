# いどばた会議室 AIが読む情報

> 作成日：2026-10-19 ／ ステータス：**方針を決めた。未実装**
>
> 数字はすべて見積もり（未実測）。

AIメンバー（ファシリテーター・メンバー3人）が、お題と背景のほかに、資料やいどばたの論点を読んで話せるようにする。

---

## 1. 今の状態（2026-10-19 時点）

| AI | 読んでいるもの |
|---|---|
| ファシリテーター・メンバー（工程2、4〜8） | お題、背景（ホストが書く4,000字まで）、みんなの声の整理、会話の全部、決まった3点 |
| みんなの声の整理（工程3） | お題、背景、ほかの参加者が工程2で書いたこと（名前は伏せる） |
| 編集者（工程9〜10） | お題、決まった3点、参加者の発言 |
| 立場づくり | お題、背景 |

資料は、ホストが手で書く「背景」しか渡せない。

---

## 2. 決めたこと

| # | 論点 | 決定 |
|---|---|---|
| 1 | 何を読ませるか | **ホストの資料**と、**いどばたで作った論点・実際の声** |
| 2 | 参加者に見せるか | **AIだけが読む**（資料そのものは画面に出さない） |
| 3 | どう読ませるか | **発言のたびに、必要な部分だけ探して渡す** |
| 4 | いどばたの論点とお題の結びつけ | **AIが近い問いを探す** |
| 5 | 「想定ユーザーの発言」とは | **いどばたの実際の声**（利用者の対話から抽出された課題・解決策）。AIが作った架空の声は使わない |

---

## 3. 読ませる情報

### 3.1 ホストの資料

- お題をつくるときにアップロードする。PDF・Word（.docx）・テキスト
- 上限：5ファイル、合計20万字（叩き台）
- 文字を取り出せない資料（スキャンした画像だけのPDFなど）は、その旨をホストに伝えて受け付けない

### 3.2 いどばたの論点と実際の声

いどばたビジョンの「問い」（`SharpQuestion`）のうち、お題に近いものを1つ見つけて、次を読み込む。

| 読むもの | 元のデータ | 渡し方 |
|---|---|---|
| 対立軸・合意点・対立点 | `DebateAnalysis`（その問いの最新版） | 短いので、**毎回そのまま**渡す |
| 実際の声（課題・解決策） | 問いに紐づく `Problem` / `Solution` の `statement` | 資料と同じく、**探して**渡す |

- 声は `statement`（抽出・要約された文）だけを使う。だれが言ったかの情報（`sourceMetadata` など）は読まない
- 工程3「みんなの声の整理」も、最初の参加者が来る前から、この対立軸・合意点を下敷きにできる（設計 v2 8.1 の d案を強める）

### 3.3 近い問いの探し方

1. お題をつくるとき、お題と背景の文と、いどばたの公開中の問い（`isVisible`）の文を、それぞれ検索用のベクトルにする
2. 一番近い問いが、決めた近さ（しきい値）を超えていれば紐づける。超えなければ紐づけない
3. どの問いに紐づいたかは**ホスト用の画面に表示し、ホストが外せる**ようにする

**注意：** いどばたの声は、別の場（授業や政党のフォーラム）で集めたもの。お題の場とは集まった人が違う。AIには「別の場で集まった声」として扱わせる（3.6）。

### 3.4 必要な部分だけ探して渡す

```
お題をつくるとき
  資料 ──▶ 400字ほどの断片に分ける ──▶ 断片ごとにベクトル化 ──▶ MongoDB に保存
  いどばたの声 ──────────────────────▶ 1件ずつベクトル化 ──────▶ 同上

発言のたびに
  参加者の直前の発言＋決まった3点 ──▶ ベクトル化 ──▶ 近い断片・声を上位4件 ──▶ 指示文に添える
```

- ベクトル化は OpenAI の `text-embedding-3-small`（いどばたの python-service と同じモデル）
- 断片はお題1つで数百個ほどなので、**MongoDB から読んでサーバーの中で総当たりで比べる**。専用の検索の仕組みは使わない
- 断片の保存先は新しいコレクション（例：`KaigiDocChunk`）。**お題と同じ日に自動で削除する**（TTL）
- 既存の python-service（Chroma）は使わない。Chroma には削除の窓口がなく、「一定期間で自動削除」と合わないため
- 探す処理が失敗しても、会話は止めない（資料なしで発言を作る）

### 3.5 原価と時間（見積もり）

| 項目 | 見込み |
|---|---|
| 1回の呼び出しの量 | 今の約5,500トークン → 約7,000トークン（約3割増） |
| 1人20分の原価 | 約3〜6円 → **約4〜8円** |
| 探す費用 | 1回0.01円未満 |
| 待ち時間 | 発言ごとに0.2〜0.5秒ほど増える |
| 資料の取り込み | 20万字で数十秒。お題をつくった後に裏で行う |

### 3.6 AIの使い方のルール（指示文に書く）

- 資料に触れるときは、出どころが分かる言い方をする（「規約では〜とあります」「別の場では〜という声がありました」）
- 資料にないことは推測で言わない。「資料にはありません」と言う
- 資料の内容で参加者の意見を否定しない。問いの材料として使う
- いどばたの声は、このお題の参加者の声ではないことを踏まえて扱う
- 資料の文章を長く引き写さない（AIだけが読む資料なので）

---

## 4. 「AIだけが読む」ことの注意

- 資料そのものは画面に出さないが、AIは会話の中で資料の内容に触れる。**内容の一部は参加者に伝わる**
- お題をつくる画面に「参加者に知られて困る情報が含まれる資料は入れないでください」と表示する
- 資料と断片は、お題と同じ日に自動で削除する

---

## 5. 作るもの

| 層 | 内容 |
|---|---|
| backend | 資料のアップロード（`multer` は導入済み）、PDF・Wordから文字を取り出す（新しい依存：`pdf-parse`、`mammoth` など）、断片化とベクトル化、`KaigiDocChunk` モデル、近い問いを探して紐づける処理、発言ごとの検索、指示文への追加 |
| frontend | お題をつくる画面に資料のアップロード、ホスト用の画面に「読み込んだ資料」と「紐づいた問い」（外せる） |
| テスト | 断片化、検索の順位、近い問いのしきい値、探す処理が失敗しても会話が続くこと |
