## 0. ひとことで

- **今回の組み合わせそのものは、まだ誰も作っていない。** 質問だけするファシリテーター、黙って付箋を書く書記、ボタンで動く整理係の3つのAIを1つのボードでつなぐものは、オープンソースにも製品にも見つからなかった。スマホで歩きながら使う音声ボードも見当たらない
- **いちばん近いのは Orality（CHI 2026）。** 話した内容から図を作り、問いを出し、矛盾を見つける。12人の実験で、「考えを支えるのはどちらか」に12人中8人が Orality を選んだ（比べた相手は ChatGPT との音声対話）
- **部品ごとには手本がある。** 付箋の作り方（MindMesh）、裏で記録する作り方（OpenAI の音声エージェントの見本、Pipecat）、グループ分け（広聴AI、BERTopic）
- **最大のリスクは「見えない誘導」。** 意見の偏ったAIの手助けを使うと、本人の考えがAIの側へ寄り、多くの人は気づかない。事前の警告も事後の知らせも、有意には防げなかった。作りそのもので防ぐ必要がある
- **音声入力は今の `gpt-transcribe` のままでよい。** 無料で使える Haas-ASR（Apache-2.0）は精度が `gpt-transcribe` 並みで、次の有力候補（6.4）。ただし GPU のサーバーが必要
- **読み上げは作り方から考え直しが要る。** OpenAI の今までの読み上げの窓口（`/v1/audio/speech`）で使えるモデルは、すべて 2027-01-06 に提供終了。後継は Realtime API という別の仕組みで作る（6.2）

### 2.1 Orality の詳細

論文（arXiv 2603.02544 の本文と付録、全29ページ、CC BY 4.0）を読んでまとめた（✔）。論文のページ：https://doi.org/10.1145/3772318.3791713 （ACM）、https://arxiv.org/abs/2603.02544 （arXiv）。

#### 解こうとした問題と答え

- 考えを声に出すと整理しやすい。ただ、文字起こしは言いよどみや繰り返しが多くて読みにくい。ChatGPT と音声で話すと、会話の記録が一列に長く伸び、見返しにくく、まとめにくい。AIの返事も長すぎて、かえって要点がぼやける
- 答えは、話した内容をAIが**ノード（短い文）とつながりの図**にして、キャンバスに並べること。**チャットの画面はない**

#### 設計の進め方

```
事前調査（8人）→ 困りごと4つ → 設計目標4つ → 理論の枠組み（4つの層）→ 機能 → 実装 → 実験（12人）
```

事前調査では、研究所の8人に自分のお題（計画、創作、問題解決）を30分以上考えてもらった。Google ドキュメントの音声入力と、文字起こしを整理するAI（DeepSeek）を使い、そのあと困ったことをインタビューした。

| 見つかった困りごと | 声の例 | 設計目標 |
|---|---|---|
| 考えは行ったり来たりするのに、話した記録は一列に並ぶだけ | 「思いつくまま話した内容は、消すことも分類することもできない」 | DG1：話した内容を2次元の図にして、考えの「形」を見えるようにする |
| 自分なりの構造（時系列、過去・現在・次の一手など）で整理したい | 人によって構造がまったく違った | DG2：構造を声で決められ、何度でも組み替えられるようにする |
| 考えは言い直すたびに深まる。でも新しい話を足すと重複が増える | 「AIに合体させると繰り返しだらけになるので、最後にまとめて整理した」 | DG3：考えの変化を記録し、見返せるようにする |
| AIは便利だが、意図を読み違え、膨らませすぎる | 「AIが足した内容が硬すぎて、自分の考えからそれた」「足りないものを指摘して、もっと聞いてほしい」 | DG4：AIは必要なときだけ手助けし、主導権は本人に残す |

理論の土台は、情報分析の「意味づけ（センスメイキング）のモデル」（Pirolli & Card）を、自分の頭の中の整理に当てはめ直したもの。

| 層 | もとのモデル | Orality での中身 | 機能 |
|---|---|---|---|
| 1 | 情報を集める | 考えを外に出す | 話すとノードになる |
| 2 | 構造にまとめる | 構造を決める・組み替える | 声で並べ替える |
| 3 | 仮説を確かめる | 薄いところ・食い違いを見つける | 〔Ask Me Questions〕〔Show Me Conflicts〕 |
| 4 | 発表する | 振り返る・書き出す | 考えの変化の記録、書き出し |

#### 機能

| 機能 | 中身 |
|---|---|
| 話すとノードになる | 話した内容から、要点を**短い文**で抜き出す（キーワードではなく文）。話題ごとにまとめて図にする。2回目以降に話した分は**色を変えて**足す。話題を選んでから話すと、その話題に足される |
| 声で並べ替える | 「この3つにまとめて」「これを合わせて」「これを分けて」と声で指示すると、AIが組み直す。全体にも、選んだ部分だけにも指示できる |
| 〔Ask Me Questions〕 | ボタンを押すと、中身が薄い話題を見つけ、**問いをノードとしてその場に置く**。話題を選んでから押すと、その話題についてだけ問う |
| 〔Show Me Conflicts〕 | ボタンを押すと、ノード同士の矛盾を探し、点線でつないで矛盾の種類を書く |
| 考えの変化の記録 | 話したときや操作を終えたときに自動で保存。時間の流れに沿って前の状態を見たり、戻したりできる |
| 書き出し | 選んだ部分を、詳しいまとめ・要点だけ・箇条書きの文章にする |

**AIの問いは、本人がボタンを押したときだけ出る。** AIが自分から話しかけることはない。論文はこれを、「話を遮りうる会話の相手」から「本人の考えの図に埋め込まれた足場」へのAIの役割の転換、と位置づけている。

#### 処理の流れと技術

```
話す
 └→ 文字起こし（AssemblyAI、話しながら文字にする）
     └→ AI（GPT-5）：要点を「話題＋短い文」に分ける
         └→ 新しい話題か、既存の話題に足すかを判定
             └→ 配置
                 ├ 文の意味を数値にする（sentence-transformers）
                 ├ 話題だけを主成分分析で2次元に置く（すでに置いたものは計算し直さない）
                 ├ 短い文は、話題のまわりに放射状に並べる
                 └ 意味が近いもの（類似度0.3以上）は少し引き寄せる
```

| 部分 | 中身 |
|---|---|
| 画面 | React ＋ TypeScript、React Flow（ノードの図）、Socket.IO（リアルタイムの更新）、Material-UI |
| サーバー | Python（Flask ＋ Flask-SocketIO） |
| 抜き出しの数 | 1回の発言で、1つの話題につき**1〜3文**。4つ以上だと細切れになりすぎて重なり、少ないと抽象的になりすぎた（試して決めた） |
| 配置の方法 | 主成分分析を選んだのは、t-SNE や UMAP より速くてほぼリアルタイムで置け、全体の距離感も保ちやすいから。短い文まで主成分分析に入れると、話題から離れてしまうので入れない |

いどばたの今の作り（React、Socket.IO）とよく似ている。

#### AIへの指示文（付録 E.2 の要約）

| 機能 | 指示の要点 |
|---|---|
| 話題と短い文の抜き出し | 「あなたは話を聞く人」。キーワードではなく**短い文**で要点を抜き出す。**主語が話し手自身なら主語は書かない。** 文を「視点」（話し手の主張・判断・意見・心配など）ごとにまとめる。**1つの視点に1〜3文。** それぞれの文だけで意味が通るようにし、**似た内容の文は作らない**。出力は `[{"topic":…, "entities":[…]}]` |
| 声での組み替え | 「あなたは内容の整理係」。よくある指示は3通り：①話題の名前まで指定された新しい構造、②名前の指定がない新しい構造（AIが名前を考える）、③今の構造に話題を足す（全文から関係する文を新しく抜き出す）。**それ以外の指示は慎重に扱い、今の構造をできるだけ保つ** |
| 〔Ask Me Questions〕 | 「あなたは、考えの整理を手伝う**ファシリテーター**」。1つの話題に**1〜2問**（中身が少ない話題には2問、ある程度ある話題には1問）。自由に答えられる問い、具体的な詳細・例・気づきを引き出す、今の中身に直接関係する、経験や具体例を話してもらう、「どんな〜」「〜を説明してもらえますか」の形、**はい・いいえで答える問いは避ける**、短く具体的に |
| 〔Show Me Conflicts〕 | 文の組ごとに、5種類の矛盾（正面からの食い違い、両立しない、価値観、やり方、前提）を探す。矛盾があるか、種類、**自信の度合い（1〜10）**、理由を出す。「**選び抜くこと。同じ話題への違う見方は、必ずしも矛盾ではない**」 |
| 書き出し | 3つの形（詳しいまとめ／要点だけ／箇条書き）。どれも本人に語りかける口調で、次の一手を含める |

比べる相手の ChatGPT には、「話すたびに構造（マインドマップか要点の一覧）を出し、前の内容に足して育てていく」と指示していた。

#### 実験の結果

12人（同じ大学から募集、英語話者、男女6人ずつ）。ノートパソコンの Chrome で、静かな部屋かオンライン。本人が「頭がごちゃごちゃしている」お題を2つ選び、Orality と ChatGPT の音声対話でそれぞれ約20分ずつ考えた（順番は入れ替えて公平にした）。

| 測ったこと | 結果 |
|---|---|
| 考えを支えたのはどちらか | **Orality 8人**、ChatGPT 1人、差なし3人 |
| 全体としてどちらが好きか | Orality 6人、ChatGPT 3人、差なし3人 |
| 考えがはっきりしたか（7段階） | 終わったあと Orality 5.42、ChatGPT 4.92。**統計的な差はなし** |
| 負担感（NASA-TLX） | 差なし |
| いちばん評価が高かった機能 | 〔Ask Me Questions〕。特に**次に何を言えばいいかわからないとき**に役立った。「文ではなく問いの形だから、新しい方向が開けた」という声 |
| 評価が低かった機能 | 〔Show Me Conflicts〕。何を矛盾とするかがあいまいで、本人が気づいた矛盾を見落とすこともあった。「自動でやってほしい」「見つけたあと、どう解けばいいかわからない」という声 |
| 考えの変化の記録 | 12人中7人が使った。**前に戻せるので、安心して組み替えを試せた** |
| 書き出し | あまり使われなかった（長い文章を読むのが負担） |

使い方は3つのタイプに分かれた。

| タイプ | 人数 | 使い方 |
|---|---|---|
| 声で指揮する人 | 5人 | 話して足し、声の指示で何度も組み替える。手ではほとんど動かさない |
| 手で地図を作る人 | 4人 | 少し話しては、手でノードを並べて意味を作る。AIの並べ方をあまり信用しない |
| 話しっぱなしの人 | 3人 | 最初に一気に全部話し、指示を1回出すだけ。並べるのは「手間がかかる」とやらなかった |

ChatGPT との違い（インタビューから）：

- **Orality は「自分で結論にたどり着くよう導く」、ChatGPT は「答えをくれる」。** ChatGPT では AIの答えを「直す」ことが多く、Orality では問いに沿って「説明を広げる」ことが多かった
- Orality は大きな問題を下へ掘り下げるのに向く。ChatGPT は同じ高さで並べた要約になりがち
- **答えがほしい人には Orality が合わなかった。** 「もっと考えなきゃいけない」「まとめてくれない」という不満があった。ChatGPT の「相棒と話している感じ」が安心につながる、という声もあった
- 参加者が求めた改善：ノードが多すぎると見にくい（ひな形、キーワードの強調、自動のまとめ）、抽象度を変えて見る、別の切り口で並べ直す

論文が認めている限界：実験室での実験でお題が浅かった可能性、お題を本人が選んだので難しさがばらばら、AIの出力が不安定（分類の誤り、意図しない合体や削除、矛盾の見落とし）。

| 項目 | 状況 |
|---|---|
| コード | 論文の本文に、公開の記載は見当たらない |

#### ひとり壁打ちボードへの意味

| 点 | Orality | ひとり壁打ちボード（今の案） | 考えること |
|---|---|---|---|
| 書記の指示文 | 「主語が自分なら書かない」「1つの視点に1〜3文」「似た内容を作らない」 | 付箋0〜4枚 | **ほぼそのまま使える。** ただ Orality には元の発言の引用がない。ここは今回の設計で足す |
| ボードの配置 | すでに置いたノードは動かさない。話題だけ配置し、中身はまわりに並べる | 本人が動かした付箋は固定 | **崩さない配置の具体的な手本** |
| 話した回の色分け | あり | なし | 取り入れたい |
| 前の状態に戻す | あり（12人中7人が使った） | 整理の〔元に戻す〕 | 根拠になる。整理だけでなく、ボード全体の版を持つ |
| AIの問い | ボタンを押したときだけ。問いは**その話題の近くに問いのノードとして置く** | ファシリテーターが毎回チャットで問う | Orality は「AIが話を遮らない」ことを利点としつつ、「もっと自分から動いてほしい」という声もあった。**毎回問うか、問いの付箋を置いて本人が選ぶか**が決めどころ。チャットで問うと「何のことかわからない」という声もあった |
| 整理 | 声で指示できる | ボタン | 「これとこれを合わせて」を**声で言える**と、歩きながらでも整理できる |
| 組み替えの安全策 | わからない指示なら今の構造をできるだけ保つ | 整理は案として見せる | 整理係の指示文に入れる |
| 矛盾 | ボタンで探す（評価は低め）。自信の度合いを出させている | 書記が自動で印を付ける | **自信が高いものだけ印を付ける**。印は控えめに見せる |
| 端末と場所 | ノートパソコン、静かな部屋 | スマホ、屋外 | 手で並べる使い方はスマホでは難しい。歩きながらだと「話しっぱなしの人」の使い方に近くなりそう |

## 4. ファシリテーションについて研究からわかっていること

| 研究 | わかったこと | 今回への意味 | 確かめ方 |
|---|---|---|---|
| Thinking Assistants（Soya Park, Hari Subramonyam, Chinmay Kulkarni。arXiv 2312.06024） | 80人のオンライン実験で4つの条件（日記だけ／問いだけ／助言だけ／問い＋情報）を比べた。「問い＋情報」が、外部の評価者が数えた考えの量で、ほかの条件より有意に多かった。**本人の自己評価には差がなかった。** また、初期の版（v1）の実地運用（223の会話）では、はっきりした答えをくれないことへの不満が見られた | **結論は出さないが、頼まれたら考える材料（観点の候補など）は出す**、という線引きが現実的 | ✔ |
| "Don't Just Tell Me, Ask Me"（Danry, Pataranutaporn, Mao, Maes。CHI 2023） | 204人の実験。AIが問いの形で示すと、何も示さない場合や、常に正しいAIが説明する場合よりも、論理的に誤った主張を見抜く精度が有意に上がった（対象は、社会的に意見が割れる主張） | 問い中心で進める根拠 | ○ |
| "AI Should Challenge, Not Obey"（Sarkar。Communications of the ACM 67(10)、2024） | AIは従順な助手ではなく、反論や代案を出して考えを支えるべき。ただし「批判を浴びせ続けると、使う人はいら立つ」とも書いている | 問い詰める強さの調整が要る | ✔ |
| MindfulDiary（Taewan Kim ほか。CHI 2024） | AIと話しながら日記を書く。段階ごとの会話の型と、自由な対話を両立させた。4週間の実地研究で、対象は**大うつ病性障害の患者28人と精神科医5人**（臨床の場の研究） | **段階（広げる → 深める → 整理する）ごとに問いの型を決める**、の参考。対象者が違うことに注意 | ✔ |
| Columbia の音声討論研究（Jain & Wang。arXiv 2603.27073、2026-03） | AIを相手にした957件の討論（MBA・EMBA の学生203人）。音声のほうがくどく、繰り返しが多いが、扱うアイデアの幅は広い**傾向があった**。音声か文字かは学生が自分で選んだ観察研究なので、音声が原因とまでは言えない | 音声は広げるのに向いている可能性がある。だからこそ、**書記による要約と重複のまとめが大事** | ✔ |
| NORC の深掘り質問の実験（Barari ほか。2024年5月実施、1,200人。関連論文は Survey Research Methods 2026） | AIが深掘りすると、答えの具体性と説明の詳しさは上がったが、関連性・完全さ・わかりやすさは上がらなかった。回答する体験の自己評価はやや下がり、途中でやめる人が増えた。**スマホでは体験が悪くなり、質の向上も見られなかった。** 序盤で深掘りしすぎると脱落が増える | スマホでは、深掘りしすぎると疲れる | ✔ |
| 話者交替の研究（Talking Turns。Arora ほか、ICLR 2025、arXiv 2503.01174） | 無音で発言の終わりを判定する方式は、**利用者が間を置いただけで、話し終わったと見なして話し始めてしまう**（37.1%）。話の途中への強引な割り込みは、別の方式（全二重）の問題。相づちをほとんど打たないことも共通の弱点 | **今回の「押して話す」方式は、発言の終わりを本人がボタンで決めるので、この失敗を起こしにくい** | ✔ |

**今回への読み方：** Habermas Machine は集団での話し合いの研究。一人のボードでは、「整理係の案に、本人の考えが寄っていく」おそれとして読む（これは私たちの解釈）。

**よい例：** Argyle ほか（PNAS 2023。題名は「Leveraging AI for democratic discourse: Chat interventions can improve online political conversations at scale」）は、1,574人が銃規制について話す場で、AIの手助けを「言い換えの案を3つ出す」ことだけに絞った。本人は採用・編集・元の文のまま送る、を選べ、約3分の2が採用した。会話の質と口調が良くなり、分断が減った一方、政策への態度は変わらなかった。**AIの手助けを「中身」ではなく「形」に限る**設計の手本になる（✔）。

- どの方式でも、iPhone では「最初に画面を押した操作の中で音を解除する」作りが要る。「押して話す」ボタンを押した瞬間に解除するのが自然。画面を消している間の再生は、どの方式でも保証されないので実機で確かめる（△）

### 6.3 似たもの探し（埋め込み）とグループ分け

| モデル | 中身 | 確かめ方 |
|---|---|---|
| OpenAI `text-embedding-3-small` | 100万トークンで $0.02（large は $0.13）。付箋100枚でもほぼ0円 | ✔ |
| ruri-v3（30m・70m・130m・310m、すべて Apache-2.0。cl-nagoya） | 日本語の評価（JMTEB）で、グループ分けと全体平均の点数は 30m 52.12/74.51、70m 52.70/75.48、130m 55.36/76.55、310m 55.69/77.24。**130m と 310m は説明書の比較表で1位と2位。** 30m は、いくつかのモデルより下 | ✔ |
| multilingual-e5（ブラウザ用の版 Xenova/multilingual-e5-small あり。元の版は MIT） | ブラウザや Node でそのまま動く | ✔ |

ruri-v3 の説明書の比較表では、`text-embedding-3-small`（51.06/70.86）と multilingual-e5-small（46.91/69.52）は、ruri-v3-30m より点数が低い（✔）。

**一人のボードへの提案（私たちの案）：** 付箋は短く、100枚以下の想定。

- **グループ分け**：付箋をまとめてAIに渡し、グループ分けと名前付けを一度に行う。少ない件数なら、質も費用も、これがいちばん扱いやすい見込み
- **2軸への配置**：両端の言葉（例：「すぐできる」⇔「時間がかかる」）との似たもの度合いの差から、各付箋の位置を計算する。同じ入力なら毎回同じ位置になり、ほぼ0円。AIによる配置の補助に使える

### 6.4 Haas-ASR（相談の中で紹介された候補）

リポジトリ（https://github.com/third-intelligence/Haas-ASR 、最新の更新 2026-10-30、版 0.1.0）、Hugging Face のモデルの説明書（https://huggingface.co/third-intelligence/Haas-ja-v1.0 ）、作者のブログ（https://third-intelligence.com/ja/posts/haas-ja-v1-release ）を開いて確かめた（✔）。

**中身**

| 項目 | 中身 |
|---|---|
| モデル | Haas-ja-v1.0（日本語専用、6.16億パラメータ）。NVIDIA の Parakeet-TDT の作りに、Kimi Linear の仕組み（Kimi Delta Attention）を組み合わせたもの |
| ライセンス | Apache-2.0（コードもモデルの重みも） |
| 精度 | 作者の評価（asr-ja-bench v1.1、5つの日本語テストを音声の長さで重み付けした平均）で文字の誤り率 6.12%。`gpt-transcribe` は 6.07%。作者が評価した無料で使えるモデルの中では最良。商用の一部（MAI-Transcribe 2 は 4.62%、ElevenLabs Scribe v2 は 5.44%、Gemini 3.1 Pro は 5.54%）はもっと良い |
| 速さ | 1回の読み取りが数十ミリ秒。Whisper large-v3 の約15倍速い（作者の評価）。リアルタイムのデモの遅れは、通信を含めて中央値 約180ミリ秒（B200 という GPU で） |
| 費用 | 作者の試算で、音声1時間あたり $0.003〜0.004（`gpt-transcribe` は約 $0.30）。**高性能な GPU（H200）を休みなく使い切った前提**で、AWS 東京・Azure 東日本の時間料金から計算したもの。運用費は含まない |
| 言葉の手がかり | 書き方と読みを登録すると、聞き取りやすくなる。話していないのに登録語を書いてしまう誤りを抑える工夫がある（それでも登録語を増やすほど、その誤りは少しずつ起きやすくなる）。手がかりを使うと処理時間は約1.3倍 |
| 長い音声 | 1回30秒まで学習。長い音声は静かなところで区切って読む |
| 動かす場所 | **Linux ＋ NVIDIA の GPU が必須。** CPU、Mac、ブラウザでは動かない |
| お試しページ | https://third-intelligence-haas-ja-v1-0.hf.space/longform （作者が公開。ファイルのアップロードは m4a や動画も受け付ける。マイクで直接録る機能、リアルタイムのタブもある） |

**今回の使い方に近いテストでの比較**（作者の評価表から。文字の誤り率、低いほど良い）

| テスト | 中身 | Haas | `gpt-transcribe` |
|---|---|---|---|
| TEDxJP | 人前で話す、自然な話し言葉 | 8.35% | **7.49%** |
| SpeechBSD | 会話 | 5.47% | **4.47%** |
| JSUT | 文章の読み上げ | **5.32%** | 6.54% |
| JVNV | 感情をこめた読み上げ | **4.53%** | 4.75% |
| FLEURS | 文章の読み上げ | 3.67% | **3.45%** |
| 加重平均 | — | 6.12% | **6.07%** |

ひとり壁打ちは「思いつくまま話す」使い方なので、近いのは TEDxJP と会話。そこでは `gpt-transcribe` が1ポイントほど良い。ただし作者によると、TEDxJP で負けている主な理由は、**Haas が「えー」「あの」などの言いよどみを書かない**こと。付箋を作る用途では、この性質がかえって都合がよい可能性がある。評価は作者自身が作ったテストによるもので、ほかの人による確認はまだ見当たらない。**雑音の中（歩きながら、電車、カフェ）のテストは含まれていない。**

**よいところ**

- 精度が `gpt-transcribe` 並みで、無料で使える。前の候補の kotoba-whisper v2.0（8.04%）、Qwen3-ASR 1.7B（7.59%）よりはっきり良い（同じ評価表で）
- **話しながら文字が出る体験が作れる。** デモでは、話している途中の音声を約0.25秒ごとに読み直し、0.7秒黙ったら（または14秒たったら）確定する。非常に速いモデルを自前で動かすからできる方法で、API で同じことをすると費用がかさむ。歩きながら「聞き取れている」と目で確かめられる
- 自前のサーバーで動かせば、**音声を外部（OpenAI）に送らずに済む**
- デモはブラウザで音声をそのまま取り出してサーバーに流す作り。iPhone（mp4）と Android（webm）で録音の形式が違う問題を避けられる

**気になるところ**

- **GPU のサーバーが別に必要。** いどばたは今 Railway で動いているが、Railway は GPU を提供していない（と理解している。要確認）。GPU を使える別のサービスに、音声入力専用のサーバーを立てることになる
- **使っていない時間も GPU の料金がかかる。** 大まかな見積もりでは、1人が1日10分話すとして、1日に数百人が使うくらいまでは `gpt-transcribe` のほうが安い。使うときだけ GPU を起こす方式は、起動に時間がかかり、「押して話す」の直後に待たされる
- 公開されたばかり（版 0.1.0）。依存するライブラリの版が厳しく固定されていて（NeMo は 2.7.3 以上 2.8 未満、flash-linear-attention は 0.5.2 だけ）、運用の手間がかかる恐れがある
- デモの「話しているか黙っているか」の判定は、決まった音量（約 -38 dBFS）で区切る。周りがうるさいと区切りが見つからず、14秒の上限でしか確定しない、と作者が書いている。屋外で使うなら工夫が要る
- GitHub の手元用デモは WAV・FLAC・MP3・OGG だけを受け付ける（m4a・mp4・webm は変換が要る）

**今の考え**

- 今は `gpt-transcribe` のまま進め、Haas は次の有力候補として持っておく
- 作るときは、音声入力の部分を差し替えられる形にしておく
- 切り替える価値が出るのは、次のどれかが当てはまったとき
  1. 使う人が増え、GPU サーバーのほうが安くなったとき
  2. 「話しながら文字が出る」体験がほしくなったとき
  3. 音声を外部に出したくない、という要望が強いとき
- **確かめ方：** 歩きながら・電車・カフェでスマホに録った同じ音声を、お試しページと `gpt-transcribe` で聞き比べる。お試しページは第三者のサーバーなので、見られて困らない内容の録音で試す
