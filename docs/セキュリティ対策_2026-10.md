# セキュリティ対策（2026-10）

> 作成日：2026-10-18 ／ ステータス：実装済み。本番の環境変数の設定とデプロイはまだ

セキュリティ監査で見つかった9件への対応。**デプロイの前に「1. デプロイの手順」の環境変数を設定すること**（設定しないと、埋め込み・クラスタリングが止まる）。

---

## 1. デプロイの手順

### 1-1. 環境変数

| 変数 | どこに | 内容 |
|---|---|---|
| `PYTHON_SERVICE_API_KEY` | **backend と python-service の両方**（同じ値） | `openssl rand -hex 32` で作る。Secret Manager か Railway の変数に入れる |
| `USER_TOKEN_SECRET` | backend（任意） | 利用者トークンの署名の鍵。未設定なら `JWT_SECRET` から作る。変えると全員が新しい ID になる |
| `ADMIN_BOOTSTRAP_TOKEN` | backend（必要なときだけ） | 最初の管理者を作るときだけ設定し、作ったら消す |

### 1-2. 順番

1. backend と python-service に `PYTHON_SERVICE_API_KEY` を設定する
2. python-service → backend → frontend・admin の順にデプロイする
   - frontend は利用者トークンを送るようになる。古い frontend のままだと、チャット・いいね・会議室が「利用者の確認ができませんでした」になる
   - backend と frontend は、できるだけ続けてデプロイする

### 1-3. Cloud Run の python-service

- `--allow-unauthenticated` のままでも、`/api/*` は鍵がないと 401 を返す
- backend は Railway で動いていて GCP の ID トークンを使えないため、IAM での保護ではなく共有の鍵にした
- `deploy/python-service.yaml` と `cloudbuild.yaml` には鍵を書いていない。Secret Manager にシークレットを作ってから、`--update-secrets PYTHON_SERVICE_API_KEY=<シークレット名>:latest` を追加する

## 2. 対応の内容

| # | 問題 | 対応 |
|---|---|---|
| 1 | python-service が認証なしで公開、CORS は全許可 | `/api/*` に `x-service-key` の確認を追加（`hmac.compare_digest`）。ブラウザからは呼ばないので CORS を外した。backend は鍵を付けて呼ぶ（`services/embedding/embeddingService.js`） |
| 2 | AI を呼ぶ API とログインに回数制限がない | `express-rate-limit`（`middleware/rateLimit.js`）。API 全体は1分600回、ログインは15分10回（成功は数えない）、AI の呼び出しは1分20回・1日300回、利用者トークンの発行は15分60回、画像は15分20回。いずれも IP ごと。policy-edit のチャットにも同じ制限 |
| 3 | 管理画面 `ReportModal` の XSS | AI が作った HTML を、`sandbox=""` の iframe（`srcDoc`）に入れた。スクリプトは動かず、管理画面の localStorage（ログイン情報）にも触れない |
| 4 | プロフィール画像の拡張子・中身を確かめていない | ファイルの先頭のバイト列で JPG・PNG・GIF を判定し、拡張子は判定した形式から決める。配信は `/uploads/profile-images` の画像の拡張子だけで、`nosniff` と `CSP: sandbox` を付ける。本人の利用者トークンが必要 |
| 5 | 利用者 ID を端末が決めるため、他人になりすませる | 下の「3. 利用者トークン」 |
| 6 | NoSQL インジェクション | `$` で始まるキーを含む本文・クエリ・パスを 400 で断る（`middleware/rejectMongoOperators.js`）。mongoose の `sanitizeFilter` は、サーバー側の `$in` なども止めてしまうので使っていない |
| 7 | セキュリティヘッダーがない | backend に `helmet`。プロフィール画像を別ドメインのフロントで表示するため、`Cross-Origin-Resource-Policy` は `cross-origin` |
| 8 | 管理者の初期化と「全管理者削除」で乗っ取れる | `DELETE /api/auth/admin-users/all` を廃止。`/api/auth/initialize` は `ADMIN_BOOTSTRAP_TOKEN` が合うときだけ（ヘッダー `x-admin-bootstrap-token`）。最後の admin は削除できない |
| 9 | Socket.IO に認証がない | 接続時に利用者トークンを確かめる（`services/socketHandlers.js`）。スレッドの更新はスレッドの本人だけが受け取れる。テーマと会議室の壁は公開の情報なので、ID の形式だけを確かめる |

## 3. 利用者トークン

- **形式**：`<userId の base64url>.<HMAC-SHA256>`（`services/userToken.js`）
  - frontend は `POST /api/users/session` で受け取り、`x-user-token` ヘッダーで送る
- **本人確認する操作**：サーバーは本文やクエリの `userId` ではなく、トークンの `userId` を使う
  - チャットの送信・読み出し・抽出
  - いいね
  - 表示名とプロフィール画像の変更
  - いどばた会議室のセッション
  - Socket.IO のスレッドの購読
- **以前からの利用者の引き継ぎ**：トークンを持たない端末が、以前から使っている ID を送ってきたとき
  - **まだ誰もその ID のトークンを受け取っていなければ**、その ID のトークンを出す（`UserTokenClaim` に記録）
  - すでに受け取られていれば、新しい ID になる
  - 他人の ID を知っていれば、本人より先に名乗り出られる隙はある
    - この隙を狭めるため、スレッドの応答から `userId` を外した
    - 本人が一度でもサイトを開けば、その ID は本人のものになる
- **質問へのいいね**：以前は誰でも何回でも足せて、誰のいいねでも消せた。今は利用者ごとに1回で、消せるのは自分のいいねだけ

## 4. 変わる動き

- 以前のチャット画面だけが使っていた ID（localStorage の `userId`）は、新しい ID（`idobataUserId`）がない端末でだけ引き継ぐ
- 回数制限の記録はプロセスのメモリにある。backend を複数台にするときは、Redis などの共有ストアに替える
- フロントエンド（nginx）の CSP はまだ付けていない。イラスト要約などの iframe の動きを確かめてから入れる
