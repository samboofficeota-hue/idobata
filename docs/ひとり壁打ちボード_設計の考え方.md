## 1. 何を作るか

### 1.1 製品の芯（たたき台）

> **いつでも、どこでも、話すだけで、自分の考えが付箋になって整理されていく。**
> **AIは聞き役と記録係。考えをまとめるのも、決めるのも本人。**

### 1.2 体験のかたち

```
┌──────────── ボード（付箋がたまっていく） ─────────────┐
│  ┌──────┐   ┌──────┐   ┌──────┐                    │
│  │経験  │   │困りごと│  │気持ち │  ← 書記が貼る        │
│  │保育園の│  │送り迎え│  │焦る   │     （本人が直せる） │
│  │…     │   │が…   │   │      │                    │
│  └──────┘   └─!理由─┘  └──────┘  ← 足りないものの印  │
│       〔まとめる〕〔軸に並べる〕〔並べ替え〕 ← 本人が押す  │
└────────────────────────────────────────────────────┘
┌──────────── 会話 ──────────────────────────────────┐
│ ファシリ：さっきの「送り迎えがきつい」ですが、          │
│ 　　　　　一番きついのはどんな瞬間ですか？              │
│                                                     │
│                  ( ● 押して話す )                     │
└────────────────────────────────────────────────────┘
```

### 1.3 いどばた会議室との関係

会議室は「10工程・20分の流れ」が土台で、その中でチャットをする。ひとり壁打ちボードは**順番を入れ替え、ボードを土台にして、会議室の要素を部品として後から足す**。

```
土台：ボード ＋ 書記 ＋ ファシリテーター ＋ 整理係
  ├ 部品：みんなの声（いどばたの声を別の色の付箋で重ねる）
  ├ 部品：AIメンバー3体（付箋を見て話す）
  ├ 部品：時間や段階の区切り
  ├ 部品：ストーリー・スライドにまとめる
  └ 部品：壁に貼り出す
```

- 土台だけでも、一人の壁打ちとして成り立つようにする
- 会議室とは別の入口・別のデータとして作り、会議室のコードは触らない。部品は借りる（9章）
- 会議室の延長にするか、独立したものにするかは**最終的には未決**。今は独立したものとして考える

## 2. 使う場面（決まったこと）

| 項目 | 決まったこと |
|---|---|
| 端末 | スマホ |
| 場所 | 問わない。歩きながら、電車の中、コーヒーを飲みながら |
| 入力 | **音声が基本。** 打ち込みもできる |
| 送り方 | **話したらすぐ送る。** 入力欄で直してから送る手順はなくす（会議室とは逆） |
| 直し方 | 付箋に〔直す〕ボタンを付け、本人が押したときだけ直す。音声の読み違いも、付箋で直す |
| 使い方の単位 | **1日1回、その場で完結する。** 何日にもまたがるボードは持たない |
| 読み上げ | 未決。音声入力の方式（`gpt-transcribe` のまま）を決めたうえで、費用に見合うかで判断する（8章） |

### 2.1 場所を選ばないことから出てくる要件

| 場面 | 課題 | 対応 |
|---|---|---|
| 歩きながら | 画面をじっと見られない。文字を直せない | 大きな「押して話す」ボタンを親指の届く位置に置く。直すのは後で付箋の段階で |
| 電車の中 | 声を出しにくい。周りがうるさい | 打ち込みにすぐ切り替えられる。小声でも拾えるか実地で確かめる |
| カフェ | 周りの話し声が入る | 声が入っているかの確認（会議室で作ったもの）に加え、マイクの雑音を抑える設定を使う |
| どこでも | 途中で降りる、話しかけられる | 同じ日の中なら、中断して続きから再開できる（**前提として置いた。要確認**） |
| どこでも | 人前で本音を話す | 音声は保存しない（会議室と同じ） |

## 3. 先行事例からわかったこと（要点）

詳しくは [`先行事例調査`](./ひとり壁打ちボード_先行事例調査.md)。

- 3つのAIを1つのボードでつなぐものは、まだ誰も作っていない。いちばん近いのは研究段階の Orality で、構成がほぼ同じ。方向の筋はよい
- 部品の手本はある：書記の入出力（MindMesh）、話す役が裏方を待たない作り（OpenAI の音声エージェントの見本）、グループ分け（広聴AI、BERTopic）
- **最大のリスクは見えない誘導。** 意見の偏ったAIの手助けを使うと、本人の考えがAIの側に寄り、多くの人は気づかない。事前の警告も事後の知らせも、有意には防げなかった。問いの選び方や付箋の見せ方でも同じことが起きうる（これは私たちの読み替え）
- 問いだけのAIには不満が出る。結論は出さないが、頼まれたら材料は出す
- 「押して話す」方式は、発言の終わりを本人がボタンで決める。無音で区切る方式に多い「利用者が間を置いただけで、AIが話し始めてしまう」失敗を起こしにくい
- 書記が付箋を出すタイミングとファシリテーターの発言がずれると、本人が追えなくなる（VoCa）

## 4. 原則

いどばた会議室の原則のうち、**引き継ぐもの・見直すもの・新しく足すもの**を分ける。この機能は、会議室のAIとは質が違う（複数のAIが同時に動く）ので、見直すことを前提にしている。

### 4.1 会議室の原則の扱い

| 会議室の原則 | 扱い | 理由 |
|---|---|---|
| 製品の芯「一人ひとりが自分の意見を作り切る。決めるのは本人」 | **引き継ぐ** | ボードはこれを強める道具 |
| 1 いどばた本体には触らない | 引き継ぐ | 本体が授業で使われていることは変わらない。会議室にも触らない |
| 5 根拠は元の声に結びつける | **引き継いで広げる** | 付箋も、どの発言から作ったかをたどれるようにする |
| 6 推測で埋めない。人そのものの属性は付けない | **引き継いで強める** | 書記が本人の言葉を膨らませると、本人の意見でなくなる |
| 8 保証できないことは書く | 引き継ぐ | — |
| 9 まず必要なものを加え、試してから変える | 引き継ぐ | — |
| **7 発言1回につき呼び出しは1回** | **見直す** | 複数のAIが同時に動くことが前提になる。新しい原則N5に置き換える |
| 3 20分のあいだ固定する | 見直す | ボードは使っている間ずっと育つ。固定するものは部品を足すときに決める |
| 2 写しを持たず最新を参照する | 部品を足すときに考える | いどばたの声を重ねるときに効いてくる |
| 4 キャラは3体／10 資料はAIだけが読む | 部品を足すときに考える | 土台にはキャラも資料もない |

### 4.2 新しい原則（たたき台）

#### N1　ボードは本人のもの

- AIが貼った付箋は「仮置き」。本人が直したり消したりした内容が常に勝ち、AIはそれを上書きしない
- 本人が動かした付箋は固定する。整理係も動かさない

#### N2　付箋は本人の言葉から作り、元の発言にたどれる

- 書記は、本人が言ったことを短くするだけ。言っていないことは書かない
- 付箋は元の発言の引用を持つ。押すと元の発言が出る
- 「本人の言葉」と「AIの言い換え」を見た目で分ける

#### N3　AIは1つの仕事だけをする

- 話す役（ファシリテーター）、記録する役（書記）、まとめる役（整理係）を混ぜない
- 誰が何をしたか（AIが貼ったのか、本人が直したのか）が、あとからわかるようにする

#### N4　AIの手助けは「形」に限る

- AIがするのは、問う・記録する・整理する・食い違いを指摘する、まで
- 結論は出さない。中身を足すのは、本人が頼んだときだけ（「観点の候補を出しましょうか？」と申し出る形）
- 誘導は警告では防げないので、**作りそのもので防ぐ**（7章）

#### N5　会話を待たせない。AIの予算は役ごとに決める

- 書記や整理係が遅れたり失敗したりしても、会話は止めない
- 「呼び出しを1回に抑える」のではなく、**役ごとに、いつ・どのモデルで・どれだけ動くかの予算を決める**（8章）
- 費用と、AIの利用枠への影響は、作る前に見積もる

#### N6　まとめは本人が頼んだときだけ

- グループ分け・軸に並べる・並べ替えは、本人がボタンを押したときだけ動く
- 結果は「案」として見せ、本人が採用・やり直し・元に戻すを選ぶ。答えのように見せない

### 4.3 迷ったときの判断の順番（たたき台）

1. 製品の芯に反しないか
2. ボードは本人のものか（N1）。本人の言葉からずれていないか（N2）
3. 本人の考えをAIの側に寄せていないか（N4）
4. 会話を待たせないか（N5）
5. 試して、戻せるか（原則9）

## 5. AIの役割分担

### 5.1 3つの役

| 役 | 仕事 | 話すか | 動くタイミング | 見るもの | 返すもの |
|---|---|---|---|---|---|
| **ファシリテーター** | 本人と話す。付箋を手がかりに掘り下げる | 話す | 発言のたび | 会話の履歴、ボードの要約（付箋・印・本人が直したもの）、コードが選んだ掘り下げ候補 | 返事（1〜2文、問いで終える）、どの付箋について聞いたか、問いの型 |
| **書記** | 発言を付箋にする。足りないものに印を付ける。食い違いを見つける | 話さない | 発言のたび（裏で） | 今の発言、今ある付箋の一覧（ID付き） | 付箋の追加・更新・印付けの差分 |
| **整理係** | グループ分け、軸に並べる、並べ替え | 話さない | 本人がボタンを押したときだけ | ボードの付箋すべて | 整理の案（グループと名前、軸の候補と位置） |

### 5.2 組み合わせ方：同時に呼ぶ

```
本人の発言（話し終えたら、すぐ送る）
   │
   ├─→ ファシリテーター ─→ 返事がすぐ出る
   │      ↑ 1つ前の発言までのボードを見る
   │
   └─→ 書記 ─→ 付箋が少し遅れてボードに貼られる（リアルタイムで届く）
                  │
                  ▼
             ボード（共有の黒板）←── 本人が直す・消す・動かす
                  │
〔まとめる〕など ─→ 整理係 ─→ 案を見せる ─→ 本人が採用／やり直し
```

| 比べた案 | 中身 | 採るか |
|---|---|---|
| 1つのAIが両方やる | 返事と付箋を1回で作る | 採らない。仕事を詰め込みすぎて、問いも付箋も質が落ちやすい |
| 順に呼ぶ（書記 → ファシリテーター） | 最新のボードを見て問える | 採らない。待ち時間が2回分になる |
| **同時に呼ぶ** | 待ち時間は今と同じ。付箋は少し遅れて貼られる | **採る。** ファシリテーターが見るボードは1つ前の発言までになるが、直前の発言は会話として読んでいるので困らない |

- 同じ人の発言が続けて届いたら、書記は順番に処理する（追い越さない）
- 書記が失敗しても、会話は続ける。付箋が貼られなかった発言は、あとで〔付箋にする〕で作り直せるようにする（案）
- 付箋がリアルタイムに届く仕組み（ソケット）は、会議室の壁で使っているものを借りる

#### 先行事例との比較（2026-11-01 追記）

複数のAIの組み合わせ方として、事例から3つの型が見えている。詳しくは [`先行事例調査`](./ひとり壁打ちボード_先行事例調査.md) 2.1（Orality）・2.2（VoCa）。

| 型 | 事例 | 組み方 | 良いところ | 気になるところ |
|---|---|---|---|---|
| A | Orality | 役割ごとのAIを、本人の操作で1つずつ呼ぶ。AI同士は直接やりとりせず、共有するのはボードだけ。どこに問うかや配置はコードが決める | AI同士の調整が要らない。話とボードがずれない | AIが自分から問いかけない |
| B | VoCa | 1つの司令塔AIが「話すこと」と「画面に出すこと」を組にして1回で決める。話している間は別の記録係が動く | 話と画面のずれが小さい | 遅い（中央値4.4秒）。1つのAIの負担が重い。それでもずれは起きた |
| C | 今の設計 | ファシリテーターと書記を同時に呼ぶ | 速い。1つのAIの負担が軽い | ファシリテーターが、まだ貼られていない付箋に触れるおそれ。**人で試した事例がない** |

今の設計（型C）は変えない。上の表の「1つのAIが両方やる」は型Bに近く、ずれを小さくできる利点はあるが、遅さと負担の重さから採らない。そのかわり、型Cのずれを抑えるために、次を取り入れる。

| # | 取り入れること | 出どころ |
|---|---|---|
| 1 | **ファシリテーターは、すでにボードにある付箋にだけ触れる。** 返事の中で付箋のIDを指させ、そのIDが実在するかをプログラムで確かめてから出す | VoCa の安全策 |
| 2 | **書記は、本人が話している間から動き始める。** 話している最中に仮のメモを出し、話し終えたら付箋として確定する | VoCa の記録係 |
| 3 | **話したことは、必ずボードに残す。** 「話した内容が消えてしまう」不満を避ける | VoCa の利用者の不満 |
| 4 | **AIにはボードを文字で渡す。** 付箋のID、本文、印、本人が直したかどうか。画像では渡さない | VoCa |
| 5 | **AIの出力は、決まった形に合っているか、指している先が実在するかを確かめてから反映する。** 形の定義は画面とサーバーで共有する | VoCa |
| 6 | **問いのきっかけはコードで絞る**（6.2） | Orality（中身が少ない話題をコードで選ぶ） |
| 7 | 新しい付箋は、元にした付箋の近くに置き、**すでにある付箋は動かさない** | Orality、VoCa |
| 8 | 前の内容は消さずに残し、戻せるようにする（版を持つ、ごみ箱） | Orality、VoCa |

**まだ見えていないこと：** 同時に動く2つのAIをボードで組み合わせた場合の、ずれの起き方と速さ。画面のたたき台（10章の段階0）で測る。

### 5.3 書記の付箋（データのたたき台）

| 項目 | 中身 |
|---|---|
| ID・版 | 本人とAIの編集がぶつかったとき、古い版を前提にした操作を捨てるため |
| 本文 | 短い一文 |
| 引用 | 元の発言のどの部分から作ったか（必須） |
| 元の発言 | 発言のID |
| 種類 | 例：経験・気持ち・困りごと・考え・アイデア（**種類の決め方は未決**） |
| 印 | 理由がない・具体例がない・気持ちがない・ほかの付箋と食い違う（相手の付箋のID） |
| 作った人 | AI／本人 |
| 本人が直した | 直したら、AIは上書きしない |
| 固定 | 本人が動かしたら固定する |
| 位置・グループ | 整理係の案を本人が採用したときに入る |
| 状態 | 仮置き・本人が消した、など |

- 1回の発言から、付箋は0〜4枚くらい。「はい」「そうです」のような短い発言では付箋を作らない（書記を呼ばない判断はコードでできる）
- 音声の発言はまとまりがない。行ったり来たりする話を分けるのが書記の大事な仕事

## 6. ファシリテーションの考え方

### 6.1 問いの決まり

- 1回に1つ。1〜2文。読み上げで聞いて一度で覚えられる長さ
- 本人の言葉を引いて返す（「さっき『○○』と言いましたが…」）
- 答えたことを聞き直さない
- 「いいですね」で終わらせない。事実を確かめる問いに置き換える
- 結論は出さない。頼まれたら「観点の候補」を出す

### 6.2 どの付箋を掘り下げるか

AI任せにすると、同じ付箋ばかり聞いたり、聞き漏らしたりする。会議室で「まだ話していないメンバー」をコードで数えて渡しているのと同じように、**コードで候補を絞って渡す**。

| 優先 | 条件 |
|---|---|
| 高 | 印が付いている付箋（理由がない、具体例がない、食い違い） |
| 高 | まだ一度も掘り下げていない付箋 |
| 低 | 何度も掘り下げた付箋 |
| 聞かない | 本人が消した付箋 |
| 本人の言葉で聞く | 本人が直した付箋 |

どの付箋をどれだけ掘り下げたかは記録し、偏りをあとから見られるようにする（誘導の確認にも使う）。

### 6.3 段階ごとの問いの型（たたき台）

| 段階 | 問いの型 | 移るきっかけ（案） |
|---|---|---|
| 広げる | 「ほかには？」「具体的には？」「そのときどう感じた？」 | 付箋が数枚たまるまで |
| 深める | 「なぜそう思う？」「前提は？」「逆の場合は？」 | 印の付いた付箋が残っている間 |
| 整理する | 「どれが一番大事？」「この2つはどうつながる？」 | 本人が〔まとめる〕を押したあと |

段階の移り方をコードで決めるか、ファシリテーターに任せるかは未決。

## 7. 誘導を防ぐ作り

研究では、警告を出しても誘導は防げなかった。だから画面の注意書きではなく、作りで防ぐ。

| やること | 防ぎたいこと |
|---|---|
| 書記は本人の言葉から作り、引用を必ず持つ。照合できない付箋は目立たなくする | AIの言葉が本人の言葉にすり替わる |
| 「本人の言葉」と「AIの言い換え」を見た目で分ける | AIが整理したものを自分の考えだと思い込む |
| 掘り下げる付箋はコードで均等に選ぶ。偏りを記録する | 問いの選び方で、特定の方向に寄せる |
| ファシリテーターは中身を足さない。頼まれたときだけ観点を出す | AIの意見が本人の意見になる |
| 整理は「案」として見せ、採用は本人がする。グループ名は本人の言葉を優先する | まとめに引き寄せられる |
| 「いいですね」で終わらせない | 迎合で深掘りが止まる |

## 8. 音声・費用・利用枠

### 8.1 音声

| 項目 | 方針 |
|---|---|
| 音声入力 | **`gpt-transcribe` のまま**（会議室の作りを借りる）。押して話す → もう一度押して止める → すぐ送る。マイクの雑音を抑える設定を使う。次の候補は Haas-ASR（無料・自前の GPU サーバーで動かす。[`先行事例調査`](./ひとり壁打ちボード_先行事例調査.md) 6.4）。切り替えられるよう、音声入力の部分は差し替えられる形にしておく（案） |
| 録音の長さ | 会議室は1回60秒まで。歩きながら長く話すことを考えて、延ばすか検討する（未決） |
| 読み上げ | **未決。** 判断材料は下の表。OpenAI の今までの読み上げの窓口（`/v1/audio/speech`）で使えるモデル（`tts-1`・`tts-1-hd`・`gpt-4o-mini-tts`）は、2027-01-06 にすべて提供終了する。使うなら、後継の `gpt-realtime-2.1-mini` を Realtime API（WebRTC か WebSocket でつなぐ別の仕組み）で使う。費用は実際に鳴らして測る。iPhone では「押して話す」ボタンを押した瞬間に音を解除する |

### 8.2 1回あたりの費用の見積もり

前提：1ドル150円。1回に10分話し、AIの返事が20回。**すべて見積もりで、実測ではない。**

| 部分 | 方式 | 1回あたり |
|---|---|---|
| 音声入力 | `gpt-transcribe`（1分 $0.0045） | 約7円 |
| 読み上げ（使う場合） | `gpt-realtime-2.1-mini`（音声出力 100万トークン $20） | 未確定（公式の単価はトークン単位で、1分あたりの目安は出ていない。実測する） |
| 読み上げ（使う場合） | スマホの無料の読み上げ | 0円（声の質と反応の速さに難あり） |
| ファシリテーター | 未定（会議室では対話全体で3〜6円） | 未見積もり |
| 書記 | 未定 | 未見積もり |
| 整理係 | AIでまとめて分類＋似たもの探し | 1回押すごとに1円未満〜数円 |

### 8.3 利用枠

- OpenAI の利用枠はモデルごとに数える。書記を別のモデルにすれば、ファシリテーターの枠を食わない
- いどばた本体・会議室と枠を共有するかどうかは、運用のときに決める（未決）
- 書記のモデルは、質を優先して試し、足りるなら小さいモデルに下げる（原則9）

## 9. 作りの方針（たたき台）

- 同じリポジトリの中に、会議室とは別の入口・データ・処理を作る（例：`routes/boardRoutes.js`、`services/board/`、`models/BoardSession.js`）。会議室のコードは変えない
- 会議室から借りる部品

| 部品 | 会議室での場所 |
|---|---|
| 音声入力（サーバー側） | `idea-discussion/backend/services/kaigi/transcribe.js` |
| 音声入力（画面側）、声が入っているかの確認 | `frontend/src/components/kaigi/useVoiceInput.ts`、`voiceLevel.ts` |
| AIへの同時問い合わせの上限・順番待ち | `services/kaigi/llm.js` |
| リアルタイムの更新 | `services/socketHandlers.js`、`services/kaigi/wallEvents.js` |
| ファシリテーターの受け答え（短い答え・わからない・脱線などへの応じ方） | `services/kaigi/prompts.js` の `RESPONSES` |

- ボードの画面の土台は、ライセンスが扱いやすいもの（React Flow、Excalidraw など）から選ぶ。スマホでは、付箋を自由に置く大きなキャンバスより、**縦に流れるカードの一覧 ＋ 整理したときだけの2軸の図**のほうが扱いやすい可能性がある（画面のたたき台で確かめる）
- 広聴AI（AGPL-3.0）のコードを取り込むかは、dd2030 の方針を確かめてから決める。考え方を参考にするだけなら問題ない

## 12. 確かめていないこと

- すべて机の上の検討。本物のAIでも、偽のAIでも、まだ動かしていない
- 費用は見積もり。料金の単価は公式ページで確かめた（2026-11-01）が、読み上げの1回あたりの費用は実測していない

- 付箋の質（本人の言葉からずれないか）、問いの質（深まるか、しつこくないか）、誘導が起きないかは、人に使ってもらって確かめる
